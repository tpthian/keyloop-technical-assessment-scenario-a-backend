# ADR-004: Booking guarantee via PostgreSQL exclusion constraints

Status: Accepted, 2026-11-03 (D-017, D-018, D-021, D-022, D-024, D-025, D-032, D-036). Evidence: first race `docs/evidence/spike/race.py` with trace `docs/evidence/spike/race-output.txt`; savepoint recovery `docs/evidence/spike/race_savepoint.py` with trace `docs/evidence/spike/race-savepoint-output-n8.txt`; both rerun with `make spike`. The first trace is reproduced under Evidence below.

## Context
The brief says "before confirming, check availability". A pre-check followed by an insert is a race between concurrent users. The requirement is read as: the availability checked must still hold when the record commits, so check and confirm are one atomic step. Concurrent users are not assumed away.

## Decision
Exclusion constraints on `appointment` using `btree_gist`: `(bay_id WITH =, tstzrange(start_at, end_at) WITH &&)`, `(technician_id WITH =, tstzrange(start_at, end_at) WITH &&)`, and one over the vehicle, `(dealership_id WITH =, vehicle_key WITH =, tstzrange(start_at, end_at) WITH &&)`, with no WHERE clause, so the same car cannot be booked twice at once (a violation is a final 409 `vehicle_already_booked`, recorded and replayed). `vehicle_key` is a NOT NULL column: the `vin` when given, else `id:<vehicle id>`. `CHECK (end_at > start_at)` and `CHECK (duration_minutes > 0)` on `service_type` close the empty-range hole: an empty range overlaps nothing and would stack without limit.

Rationale: exclusion constraints over time ranges are the documented PostgreSQL pattern (the manual's own example is room reservations), so `btree_gist` here is a recognised technique, not a trick.

Commit order is the arbiter. The second conflicting INSERT waits for the first transaction, then proceeds or fails with SQLSTATE 23P01. The application retries with the next candidate (free bay x free qualified technician, first-fit over a randomised order), bounded (5 attempts), in the same request, then returns 409 with a true reason: `capacity_exhausted` (final), `vehicle_already_booked` (final) or `contention` (transient; ADR-008). No promise is made about which user wins. Confirmations are never revoked.

**Deadlock clause.** When two INSERTs on the same pair are truly simultaneous, PostgreSQL may report a deadlock (40P01) instead of 23P01, because the gist entry is inserted before the conflict check: each transaction sees the other's uncommitted row and waits. The adapter maps both 23P01 and 40P01 to `ResourceTaken`, catching them only around the savepoint-wrapped appointment INSERT; a 40P01 from any other statement is a 5xx. Each caught 40P01 is counted in the event field `deadlocks`. Candidate order is randomised per request so concurrent requests spread over pairs, and the concurrency test starts both inserts behind a barrier. An attempt costs a few ms when the conflict is detected immediately, and up to `deadlock_timeout` when truly simultaneous. The booking transaction sets `SET LOCAL deadlock_timeout = '100ms'` (default 1 s) and `statement_timeout` 2 s, so five deadlocked attempts cost about 500 ms, inside the 1,000 ms good bound (latency budget below).

- Rule: `deadlock_timeout` is a superuser-level parameter, so `SET LOCAL deadlock_timeout` requires `GRANT SET ON PARAMETER deadlock_timeout` to the application role (PostgreSQL 15 and later); the migration grants it (D-036).
- Limitation: `statement_timeout` bounds one statement, not the request. No request-level deadline and no connection-pool-size rule is set; the latency budget bounds deadlock waits only.
- Evidence: the first spike's 50 ms stagger could not expose the deadlock (`docs/evidence/spike/race.py`); a separate adversarial review reproduced it live (`docs/ai/reviews/review-001.md`, finding 1); the second spike recovered four 40P01 inside one transaction (`docs/evidence/spike/race-savepoint-output-n8.txt`).

**Pruning clause.** On a lost resource, every candidate containing it is pruned, identified by the constraint name in the error (a deadlock names none, so only the attempted candidate is pruned). A violation of `no_vehicle_overlap` prunes nothing and ends the request with `vehicle_already_booked`. Otherwise the 409 code is decided on the pruned list: empty means `capacity_exhausted`, otherwise `contention` once the bound is hit.

**Coupling clause.** This is PostgreSQL-specific by choice. It is isolated behind the port `reserve(candidate) -> Confirmed | ResourceTaken`. The concurrency test runs against the port and defines the contract any replacement adapter must pass.

**Concurrency-model clause.** Safety comes from the database, not from the application's concurrency model. The app is async (FastAPI, async driver) and horizontally scaled, with no blocking calls in handlers.

**Savepoint clause.** The idempotency claim and the booking share one transaction (ADR-008), and a failed INSERT aborts a PostgreSQL transaction. Each candidate attempt is therefore wrapped in a `SAVEPOINT`, with `ROLLBACK TO SAVEPOINT` on 23P01 or 40P01 before the next candidate. The concurrency test exercises this path (V-002).

- Evidence: the first spike used one transaction per attempt and did not expose the gap (`docs/evidence/spike/race.py`). The second spike, eight clients behind a barrier, recovered from 23P01 and 40P01 by rollback to the savepoint with the key row intact (`docs/evidence/spike/race_savepoint.py`, `docs/evidence/spike/race-savepoint-output-n8.txt`).

**Tenancy clause.** The same principle applies to tenancy. `service_bay` and `technician` carry `UNIQUE (id, dealership_id)`, and `appointment` has composite foreign keys `(bay_id, dealership_id)` and `(technician_id, dealership_id)` referencing them. A bay or technician from another dealership cannot be booked, regardless of code path. Rationale for placing it here rather than in ADR-003: it is a database-enforced guarantee of the same kind as the exclusion constraints.

**Scaling clause.** The brief gives no site count; 1,000 sites x 60 bookings/day is a sizing assumption, chosen to show headroom. One primary, sized at that figure: 60,000 bookings/day is 0.7 bookings/s on average; each booking writes about 3 rows (key insert, appointment insert, key update); with a peak factor of 30 (bookings cluster in opening hours and at the start of the day) the peak is about 20 bookings/s, about 60 row writes/s. Appointment rows are retained: about 22 M rows/year at that rate. The design is unchanged for a single dealer group with a handful of sites, because tenancy by `dealership_id` does not depend on the count. Read replicas serve availability only (lag acceptable, the read is advisory); appointment reads always go to the primary, because a stateless instance cannot detect that a read follows a write; shard by `dealership_id` if ever needed (the invariant is shard-local by construction; `dealership_id` partitions every tenant table, and `skill`, `service_type` and `service_type_required_skill` are global reference data replicated to every shard); never multi-primary for one dealership.

## Latency budget

Worst case of one booking request against the SLO's 1,000 ms good bound:

| Step | Worst case | Source |
|---|---|---|
| Parse, dealership load, schema validation, hash | Not budgeted separately; measured by V-002 | |
| Key claim INSERT | Waits only behind a concurrent request with the same key | ADR-008, idempotency boundary |
| Candidate query | Measured by V-002 | |
| 5 attempts, each lost to a deadlock | 5 x 100 ms = 500 ms | `SET LOCAL deadlock_timeout = '100ms'` |
| An attempt lost to 23P01 behind an uncommitted holder | The holder's remaining transaction time | Commit-order arbitration |
| Business-rule reads, recording the response, COMMIT | Measured by V-002 | |
| Remaining for every step except deadlock waits | 1,000 - 500 = 500 ms | Arithmetic |
| Ceiling per statement | 2,000 ms; a cancelled statement ends the request as a 5xx, not stored | `statement_timeout = '2s'` on the booking path |

- Rule: a booking request slower than 1,000 ms is bad in the SLO whatever its status; a race recovered within the request is good only inside the bound.
- Fairness: the candidate order is randomised per request, so concurrent requests spread over pairs and none is favoured by its position in a fixed list. Commit order decides each conflict; no arrival-order promise is made.
- Measured figure: the concurrency test (V-002) records booking latency under concurrent load. It has not run yet, so no measured number is claimed here.
- Rejected: the default `deadlock_timeout` of 1 s; five deadlocked attempts would take about 5 s, beyond the bound.

## Scale

The brief gives no site count; 1,000 sites x 60 bookings per day is a sizing assumption, chosen to show headroom:

| Quantity | Value | Derivation |
|---|---|---|
| Bookings per day | 60,000 | 1,000 sites x 60 (sizing assumption) |
| Average bookings/s | 0.7 | 60,000 / 86,400 s |
| Row writes per booking | About 3 | Key insert, appointment insert, key update |
| Average row writes/s | About 2 | 0.7 x 3 |
| Peak factor | 30 | Assumption: bookings cluster in opening hours and at the start of the day |
| Peak bookings/s | About 20 | 0.7 x 30 |
| Peak row writes/s | About 60 | 20 x 3 |
| Appointment rows per year | About 22 M | 60,000 x 365; rows are retained, each with an entry in three GiST indexes, so index size grows with them |
| Availability work per request | At most 14 days x pairs | Window bound, ADR-010 |

## Evidence

Spike trace (A holds its transaction open 300 ms; B arrives 50 ms later wanting the same bay, technician and range). Source: `docs/evidence/spike/race.py`; trace: `docs/evidence/spike/race-output.txt`; rerun with `make spike`.

```text
[   21.1 ms] A: INSERT bay=2 tech=7 (uncommitted, holding 300 ms)
[   75.4 ms] B: INSERT bay=2 tech=7 ...
[  324.4 ms] A: COMMIT
[  326.0 ms] A: CONFIRMED bay=2 tech=7
[  327.9 ms] B: LOST bay=2 tech=7 -> no_bay_overlap (23P01), next candidate
[  328.0 ms] B: INSERT bay=3 tech=9 ...
[  329.7 ms] B: CONFIRMED bay=3 tech=9
```

B blocks inside PostgreSQL on A's uncommitted row, with no application lock, then loses; the constraint name in the error lets the adapter tell a resource conflict from any other failure.

## Alternatives rejected
- FIFO single-writer queue: asynchronous "accepted" response, a broker, a throughput cap. Right for stadium ticketing, wrong here.
- Application-level lock: not valid across instances.
- `SELECT ... FOR UPDATE`: pessimistic, serialises non-overlapping bookings, and protects only code paths that follow the discipline. Kept as the fallback adapter.
- Availability counter as decision input: a derived value that can drift from the calendar.

## Consequences
Non-overlap (bay, technician, vehicle) and tenancy hold for any writer, including a future script or second service. Qualification, `end_at = start_at + duration` and opening hours are enforced on the single write path, the booking service. Each attempt needs a savepoint, since a failed statement aborts a PostgreSQL transaction. The transaction runs at READ COMMITTED (the PostgreSQL default), which the idempotency `ON CONFLICT` path requires. The constraints stay unconditional because cancellation is out of scope. When cancel arrives they take the partial form `EXCLUDE USING gist (...) WHERE (status = 'confirmed')`; the real-world cancel paths are a reminder message with a cancel link and a customer-service-initiated cancel.
