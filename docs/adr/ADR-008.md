# ADR-008: Idempotency

Status: Accepted, 2026-11-03 (D-015, D-018, D-019, D-024, D-032, D-036)

## Context
Clients retry on timeouts. A retry must not create a second appointment, but a deliberate later booking must still work.

## Decision
A mandatory, client-generated `Idempotency-Key` header, scoped per dealership, stored with a hash of the canonical request. The key must be a UUID (400 otherwise), so the key written to every booking event cannot carry personal data. The key is claimed with `INSERT ... ON CONFLICT DO NOTHING` inside the booking transaction. The transaction runs at READ COMMITTED, a stated requirement: the `ON CONFLICT` path would otherwise surface serialisation failures (40001).

Order of a booking request (design.md section 3 holds the sequence diagram; the full event table is under Idempotency boundary below):

| Step | Failure response | Stored on key |
|---|---|---|
| 1. Parse JSON, check the key is a UUID | 400 | No |
| 2. Load the dealership | 404 `not_found` | No |
| 3. Validate the schema (types, at least one identifier) | 422 `validation` | No |
| 4. Canonicalise with the dealership zone and hash | | |
| 5. BEGIN, claim the key | Existing key: replay (same hash) or 422 `replay_conflict` (different hash) | Existing row unchanged |
| 5a. `UnitOfWork.serialise(dealership_id)`: transaction-scoped advisory lock, only when the claim returned no row (ADR-004 amendment, D-048) | | |
| 6. Business validation: outside hours, past or beyond horizon, gap time, unknown service type, no qualified technician | 422 `validation` | Yes |
| 7. Candidate query, then up to 5 attempts | 201, 409 `capacity_exhausted`, 409 `vehicle_already_booked` (final); 409 `contention` (transient) | Final outcomes only |

- Rule: the hash covers the canonical form of the schema-validated request (sorted keys, no whitespace, nulls omitted, start converted to UTC in the dealership zone), so formatting differences do not make a retry look different.
- Rule: record final outcomes only: 201, 409 `capacity_exhausted`, 409 `vehicle_already_booked` and the business 422s of step 6. Responses of steps 1 to 3 are never stored.
- Rule: a 5xx rolls back, so a retry runs again. A concurrent duplicate blocks on the unique index until the first request ends.
- Rule: a stored outcome replays until cleanup removes the key, at least 24 h after creation. Cleanup is documented SQL, not a scheduled job.

Because the key claim and the booking share one transaction and a failed INSERT aborts a PostgreSQL transaction, each candidate attempt is wrapped in a `SAVEPOINT`, with `ROLLBACK TO SAVEPOINT` on 23P01 or 40P01 (ADR-004); on a 23P01 every candidate containing the named resource is pruned; a 40P01 names no resource and prunes nothing (ADR-004 amendment, D-048). The concurrency test must exercise this path.

| 409 code | Condition | Class |
|---|---|---|
| `vehicle_already_booked` | 23P01 on `no_vehicle_overlap` | Final: recorded on the key and replayed |
| `capacity_exhausted` | Pruned candidate list empty | Final: recorded on the key and replayed |
| `contention` | Bound of 5 hit, candidates left | Transient: the whole transaction rolls back, discarding the key claim; returned with `Retry-After: 1`; the client retries with the same key and the server recomputes candidates |

- Rule: the booking transaction sets `SET LOCAL deadlock_timeout = '100ms'` and `statement_timeout` 2 s. Five deadlocked attempts would cost about 500 ms of detection waits, inside the 1,000 ms good bound of the SLO; now that bookings of one dealership are serialised (D-048) that is the allocated cost of an unexpected 40P01, not an enforced ceiling, since no request deadline exists (ADR-004, latency budget). A request over the bound counts as bad whatever its status.
- Rationale for the bound of 5: it stops a walk over a long bay x technician list.

## Idempotency boundary

- Rule: the hash covers the canonical schema-validated request (sorted keys, no whitespace, nulls omitted, start converted to UTC in the dealership zone, first occurrence for a repeated time). A gap time still hashes deterministically and is rejected after the claim.

| Event | Response | Stored on key? | On client retry with the same key |
|---|---|---|---|
| Malformed JSON | 400 `validation` | No, before BEGIN | Validated again; same bytes, same 400 |
| Key missing or not a UUID | 400 `validation` | No, before BEGIN | Validated again |
| Unknown dealership | 404 `not_found` | No, before BEGIN (no zone to hash with) | 404 again |
| Schema-invalid body, no identifier | 422 `validation` | No, before BEGIN | Validated again; a corrected body under the same key runs as a first request |
| Outside hours, past or beyond horizon, gap time, unknown service type, no qualified technician | 422 `validation` | Yes | Same body: stored 422 replayed. Different body: 422 `replay_conflict` |
| Concurrent request, same key, same body | Second blocks on the unique index; replays the first's stored response | The first request's final outcome | If the first rolled back (`contention`, 5xx), the second claims the key and runs |
| Same key, different body | 422 `replay_conflict` | No; stored row unchanged | 422 `replay_conflict` again |
| 23P01 on an attempt (bay or technician) | None yet: rollback to the savepoint, prune the resource, next candidate | Claim survives the savepoint rollback | Not visible to the client |
| 40P01 on an attempt (not expected once serialised, D-048) | None yet: rollback to the savepoint, count in `attempts` and `deadlocks`, keep the candidate list, bound of 5 still applies | Claim survives | Not visible to the client |
| `capacity_exhausted` | 409, final | Yes | Replayed; a new search needs a new key |
| `vehicle_already_booked` | 409, final | Yes | Replayed |
| `contention` (bound hit, candidates left) | 409, `Retry-After: 1` | No; full ROLLBACK discards the claim | Runs again; candidates recomputed |
| Crash after claim, before COMMIT | Client sees an error or timeout | No; key, appointment and response roll back together | Runs again |
| Crash after COMMIT, before response | Client sees a timeout | Yes; key, appointment and 201 committed together | Stored 201 replayed, same appointment |
| 5xx (database error, 40P01 outside the attempt INSERT, `statement_timeout`) | 5xx `error` | No; rolled back | Runs again |

## Alternatives rejected
- Key derived from request content: a retry and a deliberate later rebooking of the same car at the same time after a cancellation are indistinguishable by content. (A second concurrent booking of the same car is refused by `no_vehicle_overlap`, not by the key.)
- No idempotency, relying on the exclusion constraint: a retry would see its own first booking as a conflict and return a misleading 409.

## Consequences
The key, appointment and recorded response commit atomically. The table grows until the operator runs the documented cleanup SQL; the replay window clients can rely on is "until cleanup, at least 24 h".
