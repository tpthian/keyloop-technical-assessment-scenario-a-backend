# ADR-009: Time zones and opening hours

Status: Accepted, 2026-11-03 (D-016, D-026, D-032)

## Context
Dealerships operate in local time; the database must compare instants.

## Decision
- Rule: store UTC (`timestamptz`).
- Rule: request `start_at` is local wall time in the dealership's IANA zone (no offset), converted using a zone library.
- Rule: a non-existent local time (spring-forward gap) is rejected with 422, stored on the idempotency key (ADR-008); for a repeated time (autumn fall-back) the first occurrence is used.
- Rule: the duration is an elapsed absolute duration: `end_at` is computed in UTC (convert the start to UTC, add the duration). "Wall time" means only the local input and the opening-hours check.
- Rationale: wall-time arithmetic is wrong across DST.
- Rule: a `start_at` in the past is rejected with 422, and the booking horizon is 90 days.
- Rule: opening hours are stored per dealership per weekday and seeded, are same-day (`opens_at < closes_at`, enforced by CHECK), and a missing weekday row means closed.
- Rule: the only opening-hours rule on booking is that the local `start_at`, as the client sent it and before conversion, falls in `[opens_at, closes_at)` of its weekday; a day with no row is closed.
- Rule: `end_at` is the true elapsed end and is unconstrained: it may cross midnight, closed days and a DST change.
- Assumption: the appointment holds its bay and technician throughout.
- Rule: `pickup_from` is derived, not stored: the first opening instant at or after `end_at` (possibly the same morning), skipping days with no hours row, by a bounded walk; it is returned in the 201 body and the AppointmentConfirmed event.
- Rule: "configurable" means stored, not exposed through an admin API.

## Alternatives rejected
- Fixed UTC offsets: wrong across DST.
- Hours in application config: not per dealership, not testable as data.
- Storing the end snapped to the next opening instant: because starts are only allowed inside opening hours, snapped and true ends give identical conflict sets (half-open ranges included), so the snap buys no safety, puts a calendar walk in the write path, loses the true completion time, and makes the hold length depend on the start.

## Consequences
Tests cover the start-in-hours check (local), `end_at` of a multi-day service across a DST boundary, `pickup_from` for the same-morning and closed-Sunday cases, and the gap and repeated-time rules. Opening-hours rows cannot cross midnight (that is about the hours table; appointments may). Hours changes require a migration until an admin API exists. Future work: public holidays and ad-hoc closures as a per-dealership closures table, consulted by the same start check and the `pickup_from` walk.
