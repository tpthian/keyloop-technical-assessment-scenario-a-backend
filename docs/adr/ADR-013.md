# ADR-013: Observability: one wide event per request

Status: Accepted, 2026-11-04 (D-028, D-029, D-032, D-037)

## Context
The brief asks for an observability strategy, not an observability server. The operator of the service (the business's own IT or its hosting provider, never dealership staff) must be able to answer, in order: is the guarantee holding; what is contention costing; is the booking path healthy; are clients retrying; is a dealership out of capacity. Attaching a log, metrics or tracing server later must need no change to the application.

## Decision
Every request writes one wide JSON event to stdout. The event is the product and the import contract; servers are documented extensions and are not shipped.

- Rule: identifiers only, no personal data such as email, VIN or `vehicle_key`. The idempotency key must be a UUID (400 otherwise), so the logged key cannot carry personal data.
- Rule: no metrics endpoint and no background audit process. The overlap query (overlapping appointments per bay, technician and `vehicle_key`) runs in two places only: as an assertion in the concurrency test and as the last line of `scripts/demo.sh`, where it must print 0.
- Rule: liveness and readiness are separate endpoints (`/health/live`, `/health/ready`). Rationale: one endpoint returning 503 on a database outage gets a healthy process restarted.

## Event schema v1

Booking-only fields are null on other routes. On `book_appointment`, the counters (`attempts`, `deadlocks`, `candidates_pruned`) and `replay` are set from the use case's outcome, so they are also null when the request ends before one: 400, 404, schema 422, `replay_conflict` and 5xx.

| Field | Type | Null when | Meaning |
|---|---|---|---|
| `v` | integer | Never | Schema version, 1 |
| `ts` | string | Never | UTC timestamp |
| `request_id` | string | Never | Per-request correlation id |
| `route` | string | Never | Operation name: `book_appointment`, `get_availability`, `get_appointment`, `health_live`, `health_ready` |
| `outcome` | integer | Never | HTTP status |
| `code` | string | 2xx on a route other than `book_appointment` | Domain code: `confirmed`, `capacity_exhausted`, `contention`, `vehicle_already_booked`, `validation`, `replay_conflict`, `not_found`, `error` |
| `final` | boolean | Never | False for `contention` and 5xx (transient); true otherwise |
| `dealership_id` | identifier | Health routes | Dealership acted on |
| `idempotency_key` | string | Not `book_appointment`, or key missing or invalid | The client's key, a UUID |
| `service_type_id` | identifier | Not booking or availability, or before schema validation | Service type requested |
| `attempts` | integer | Not `book_appointment` | Candidate pairs tried |
| `deadlocks` | integer | Not `book_appointment` | Attempts lost to 40P01 |
| `candidates_pruned` | integer | Not `book_appointment` | Candidates pruned after a lost race |
| `replay` | boolean | Not `book_appointment` | Stored outcome replayed |
| `bay_id` | identifier | Not a 201 | Winning bay |
| `technician_id` | identifier | Not a 201 | Winning technician |
| `latency_ms` | integer | Never | Time taken by the service |

## SLI

The SLI covers `route = book_appointment` only. The target is 99.5 per cent good over 30 days.

| Booking response | SLI class |
|---|---|
| 201 `confirmed`, `latency_ms` at most 1,000 | Good |
| 409 `capacity_exhausted` or `vehicle_already_booked`, at most 1,000 ms | Good |
| 422 `validation` or `replay_conflict`, at most 1,000 ms | Good |
| Replay of any stored outcome, at most 1,000 ms | Good |
| Any of the above, over 1,000 ms | Bad |
| 409 `contention` | Bad |
| 5xx `error` | Bad |
| 400 `validation`, 413 `validation` (body over the cap, ADR-014), 404 `not_found` | Excluded: the request never reached a booking decision |

- Rule: response time is best measured where the client sees it; `latency_ms` is the service's own timer, so the operator also times at the edge.

## Extensions, not built
- Without code change: a log shipper to a log or event store; metrics, dashboards and burn-rate alerts derived from the events there.
- With instrumentation code: OpenTelemetry traces, the wide event as the root span and one child span per attempt.
- Business reporting: SQL over the appointment table plus outcome counts from the events.

## Alternatives rejected
- A `/metrics` endpoint with pre-aggregated views and a 60 s in-process overlap audit (D-028, M11 of review-002): an aggregation endpoint and a scheduled process are scope beyond a strategy, and both can be attached later from the event stream (D-037).
- Pre-aggregated metrics as the primary record: aggregation at write time cannot be undone, and high-cardinality keys belong in events, not labels.

## Consequences
- Limitation: until a store is attached there is no history beyond container log retention and no alerting.
- Tension: preventing write skew in general requires serializable isolation; the service uses READ COMMITTED with exclusion constraints, which that rule does not name.
- Tension: standard practice favours exponential backoff; at this scale the service uses a cap of five attempts and `Retry-After`.
- Tension: sharding by dealership keeps constraints shard-local only if each vehicle and technician belongs to one dealership. Assumption: each does.
