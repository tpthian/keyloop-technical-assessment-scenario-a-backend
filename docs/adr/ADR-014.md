# ADR-014: Security posture and trust boundary

Status: Accepted, 2026-11-05 (D-058; builds on D-014 and D-025). This record states a posture and the controls behind it; it is not a penetration test, and no penetration test has been run.

## Context
The brief states no security requirement. The service is one component behind a platform gateway, and it may later exchange data with a CRM. Until this record, the only statement was the design's assumption row "Authentication: upstream gateway; out of scope" (D-025). That leaves the trust boundary implied: what the gateway must supply, what the service guarantees on its own, and what stays open are not written down.

## Decision
Three trust zones, each with its own controls. The service trusts the gateway for identity and volume, trusts nothing in the request body, and never trusts the CRM on the booking path.

- Rationale: authentication, rate limiting and volumetric defence are platform concerns that every service behind the gateway shares; the controls that depend on the booking domain (what a valid request is, how much work one request may cause, what reaches the logs) can only live in the service.

**(a) Gateway, assumed, not in this repository.** TLS termination; authentication of the caller; rate limits per caller and per dealership; a request body size cap; a WAF and volumetric protection against botnets and DDoS. Contract below.

**(b) This service.** What it does itself, each item in code:

| Control | Where |
|---|---|
| Parameterised SQL through SQLAlchemy Core: every statement that carries request data binds its values, so there is no injection path. The two `SET LOCAL` statements interpolate module constants, never input | `src/scheduler/infrastructure/postgres/repositories.py`, `unit_of_work.py:46-47,70` |
| Pydantic validation of every body and path parameter; unknown fields refused (`extra="forbid"`); a schema 422 is never stored (ADR-008) | `src/scheduler/interfaces/http/schemas.py`, `appointments.py`, `availability.py` |
| Upper bound on every free string: customer `id` and vehicle `id` 64, `email` 254, `name` 200, raw `vin` 32, `make` and `model` 100; over a bound is a schema 422 (this record) | `schemas.py` (`ID_MAX`, `EMAIL_MAX`, `NAME_MAX`, `VIN_MAX`, `MAKE_MODEL_MAX`) |
| Request body cap of 16 KiB: a declared `Content-Length` over the cap, or more bytes received than the cap, is 413 `validation` in the house error body when the handler reads the body, before the dealership load; never stored (this record) | `src/scheduler/interfaces/http/limits.py`, `errors.py`, mounted in `main.py`; TC-40 |
| Identifiers only in events, never email, VIN or `vehicle_key`; the wide event is one JSON-encoded line, so no request text can forge a log line (ADR-013) | `src/scheduler/interfaces/http/events.py` |
| Idempotency keys must be UUIDs (400 otherwise), so the logged key cannot carry personal data (ADR-008, ADR-013) | `src/scheduler/interfaces/http/dependencies.py` |
| Bounded work per request: availability window at most 14 days (ADR-010); booking at most 5 attempts (ADR-004); on the booking transaction `statement_timeout` 2 s and `deadlock_timeout` 100 ms (ADR-004); booking and availability horizon 90 days, which also bounds how far ahead slots can be hoarded (ADR-009) | `application/get_availability.py` (`MAX_SPAN`), `domain/attempts.py` (`RETRY_BOUND`), `infrastructure/postgres/unit_of_work.py` (`STATEMENT_TIMEOUT`, `DEADLOCK_TIMEOUT`), `domain/time_rules.py` (`HORIZON`) |
| Supply chain and secrets: gitleaks in pre-commit; dependencies pinned in the committed `uv.lock`; CI runs the same hooks, mypy and the tests on every push and pull request (ADR-011) | `.pre-commit-config.yaml`, `uv.lock`, `.github/workflows/ci.yml` |

**(c) Future CRM integration, not built.** Outbound only, to an allow-listed host; credentials from the environment, never the repository; a timeout and a circuit breaker on every call; never on the booking path. D-014 already keeps the CRM off the booking path for availability (ADR-007); the security reason is the same rule: a compromised or slow CRM cannot block or corrupt a booking. Any inbound webhook is signature-verified and its body treated as untrusted input, validated like a request.

- Rule: a 413 is a pre-claim refusal like a 400: never stored on the key, and outside the booking SLI because the request never reached a booking decision (ADR-013).
- Rule: `/docs` and `/openapi.json` are served in development and in the demo (ADR-012), with FastAPI's defaults, in every environment today. Requirement, deferred: production disables or gates them through a setting (for example `docs_url=None` and `openapi_url=None` when `APP_ENV` is production). No such setting exists yet; the demo surface is unchanged.

## Gateway contract

What the service assumes the gateway supplies. None of it is verified by the service today.

| The gateway supplies | Why the service needs it |
|---|---|
| TLS termination; plain HTTP only on the private network behind it | The service listens on plain HTTP (`uvicorn` in `docker-compose.yml`) |
| An authenticated caller; unauthenticated requests never reach the service | The service has no authentication of its own |
| A trusted dealership claim for the caller (a signed token claim, or a header the gateway sets and strips from client input), which the service compares with the `dealership_id` in the path | Tenant binding; not implemented, see the gap below |
| Rate limits per caller and per dealership | Bounds slot hoarding by volume and the queue behind one dealership's lock |
| A request body size cap at or below the service's 16 KiB | The service cap is defence in depth, not the first line |
| WAF and volumetric protection (botnets, DDoS) | The service has no defence against volume beyond its per-request bounds |

- Gap, known and stated: tenant binding. Every route is scoped by the `dealership_id` in the path, and the database refuses cross-dealership rows (composite foreign keys, ADR-004), but nothing ties the caller to that dealership. An authenticated caller of dealership 1 can book at, or read an appointment of, dealership 2 by naming it: an insecure direct object reference. Closing it is a Contract-level change (a claim in the gateway contract, a comparison in the HTTP layer, a 403 code and its tests). It is deferred, not forgotten.

## Threats

Where: in code (this repository enforces it), gateway (assumed above), deferred (named, not built).

| Threat | Control | Where | Evidence |
|---|---|---|---|
| SQL injection | Bound parameters through SQLAlchemy Core; no request value is interpolated into SQL | In code | `infrastructure/postgres/repositories.py`, `unit_of_work.py` |
| Cross-site scripting | Not applicable to the API: its routes answer JSON and render no request data as HTML. The one HTML page is FastAPI's Swagger UI at `/docs`, a static page that renders the OpenAPI document, not stored data; it is covered by the last row. The injection classes that apply are SQL and log injection, both closed: SQL by bound parameters, logs by JSON-encoded events carrying identifiers only | In code | `events.py`, ADR-013 |
| Tenant confusion, insecure direct object reference | Path scoping and composite tenancy foreign keys today; caller-to-dealership binding needs the gateway's dealership claim | Deferred (gateway claim plus service comparison) | Gateway contract above; ADR-004 |
| Volumetric denial of service | Rate limits, WAF, body cap at the gateway; per-request bounds in the service | Gateway; in code for the per-request bounds | Decision (b) above |
| Oversized body or strings | 16 KiB body cap (413); `max_length` on every free string (422) | In code | `limits.py`, `schemas.py`, TC-40 |
| Hot dealership: bookings queued on one dealership's advisory lock each hold a pooled connection, up to the 2 s `statement_timeout`, and can drain the pool (10 plus 10 overflow per instance) for every other dealership | Per-dealership rate limit at the gateway; in the service, a `lock_timeout` on the lock statement plus an in-process semaphore per dealership taken before a pooled connection | Gateway; service controls deferred | ADR-004, Latency budget and Amendment; `engine.py` |
| Slot hoarding | Horizon of 90 days bounds how far ahead; per-caller rate limit bounds how many; no per-customer quota | In code (horizon); gateway (rate); quota deferred | ADR-009, `domain/time_rules.py` |
| Personal data at rest: customer email and name, VIN and `vehicle_key` in the appointment snapshot; the stored 201 body on the idempotency key repeats the customer and vehicle | Kept out of events (ADR-013); retention of appointments is the operator's; stored keys are removed by the cleanup statement in the README (no job is shipped) | In code (events); operator (retention) | `events.py`, README "Known limitations" |
| Secrets in the repository | gitleaks in pre-commit and in CI; configuration from the environment (`DATABASE_URL`) | In code | `.pre-commit-config.yaml`, `src/scheduler/settings.py` |
| Supply chain | Dependencies pinned in `uv.lock`; CI on every push and pull request; no dependency bots (ADR-011 scope guard) | In code | `uv.lock`, `.github/workflows/ci.yml` |
| Exposed Swagger UI and OpenAPI document | Served in every environment today (FastAPI defaults), as development and the demo need; requirement, not built: a setting that disables or gates them in production | Deferred (document only) | ADR-012; this record |

## Alternatives rejected
- Authentication inside the service: duplicates the platform gateway and adds one more secret store to operate and rotate.
- Per-request CRM validation of customer and vehicle: puts the CRM on the booking path, against D-014 (ADR-007).
- No security record at all: leaves the integration boundary implied, the one loose end a reviewer of a service behind a gateway would ask about.

## Consequences
- Limitation: tenant binding is open until the gateway claim and the service comparison are built; until then the service is safe only behind a gateway that routes each caller to its own dealership's paths.
- Limitation: the hot-dealership controls in the service are deferred; until they exist, the gateway's per-dealership rate limit is the only bound on the lock queue.
- Scope guard: no authentication, authorisation, quota or CRM client is built in this repository (ADR-012).
