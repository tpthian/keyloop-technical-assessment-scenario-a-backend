# ADR-010: Availability is advisory

Status: Accepted, 2026-11-03 (D-017, D-026, D-032, D-036)

## Context
Users want to see options before booking. Anything shown can be taken before they act.

## Decision
`GET /availability` returns start windows: for each (bay, qualified technician) pair and each local day, the pair's free interval with the service duration subtracted from its right end on UTC instants, then intersected with that day's local opening hours, within `[from, to)`, with `as_of`.

- Rule: `[from, to)` spans at most 14 days and lies inside the 90-day booking horizon; otherwise 422. The result is bounded by days x pairs.
- Rule: `as_of` is a data watermark, not the response time: `pg_last_xact_replay_timestamp()` on a replica, `now()` on the primary. Commits after `as_of` may be missing.
- Rationale: wall-time subtraction across a DST change would advertise starts the UTC booking range refuses. Worked example below.
- Rule: it is a separate read-only query, not the booking candidate query, which answers a single start time. It carries no guarantee; the booking attempt is authoritative.

## Worked example

Dealership in `Europe/London`, open 08:00 to 18:00 Monday to Saturday, closed Sunday. Service of 4,320 min (72 h). One qualified pair, bay B1 and technician T1. Clocks go forward on Sun 2027-03-28 at 01:00 UTC (01:00 GMT becomes 02:00 BST). Existing on B1/T1: E1 ending Fri 2027-03-26 09:00 GMT; E2 on Mon 2027-03-29 12:00 to 14:00 BST. Request: `from=2027-03-26&to=2027-03-30`, issued Thu 2027-03-25 16:00:00 UTC.

| Item | Local | UTC | Why |
|---|---|---|---|
| E1 end | Fri 26 Mar 09:00 GMT | 2027-03-26 09:00Z | Existing appointment |
| E2 | Mon 29 Mar 12:00 to 14:00 BST | 2027-03-29 11:00Z to 13:00Z | Existing appointment |
| Free interval of B1/T1 | Fri 09:00 GMT to Mon 12:00 BST | 26th 09:00Z to 29th 11:00Z (74 h) | Between E1 end and E2 start |
| Latest start before E2 | Fri 11:00 GMT | 29th 11:00Z - 72 h = 26th 11:00Z | Duration subtracted on UTC instants |
| Window, Friday | `[09:00, 11:00]` GMT | `[09:00Z, 11:00Z]` | Inside Friday hours. A 09:00 start begins as E1 ends; an 11:00 start ends as E2 begins; half-open ranges allow both |
| Window, Saturday | None | | Every Saturday start ends after E2 begins (Sat 08:00 + 72 h = Tue 09:00 BST) |
| Window, Sunday | None | | Closed |
| Window, Monday | `[14:00, 18:00)` BST | `[13:00Z, 17:00Z)` | Free after E2 ends; the start must be before closing |
| Booking at Fri 09:00: `start_at` | Fri 26 Mar 09:00 GMT | 2027-03-26 09:00Z | Inside Friday hours |
| `end_at` | Mon 29 Mar 10:00 BST | 2027-03-29 09:00Z | 72 h elapsed; the wall clock shows 73 h because the clocks went forward |
| `pickup_from` | Mon 29 Mar 10:00 BST | 2027-03-29 09:00Z | `end_at` falls inside Monday hours, so the first opening instant at or after it is `end_at` |
| Rejected: wall-time subtraction | Mon 12:00 - 72 h = Fri 12:00 | | Would extend Friday's window to 12:00; an 11:30 GMT start ends 12:30 BST, overlaps E2, and booking refuses it |
| Replica 30 s behind | | `as_of` = 2027-03-25 15:59:30Z | E2 committed on the primary at 15:59:45Z, after the watermark, so the replica omits it |
| What the replica returns | Fri `[09:00, 18:00)` GMT, Sat `[08:00, 18:00)` GMT, Mon `[08:00, 18:00)` BST | | Without E2 the pair looks free from Fri 09:00 GMT onward. A booking from an extra window reaches the primary, hits E2's constraint and gets 409 `capacity_exhausted` (one pair). `as_of` tells the client which commits the answer reflects |

## Alternatives rejected
- Hold with TTL: adds a reservation state machine, expiry, and the risk of abandoned holds blocking real customers, to solve a case the booking path already handles.
- Availability counter: can drift from the calendar.

## Consequences
Staleness is by design and visible through `as_of`, which states the last commit the answer reflects. Availability reads can later move to replicas without affecting correctness; appointment reads stay on the primary.
